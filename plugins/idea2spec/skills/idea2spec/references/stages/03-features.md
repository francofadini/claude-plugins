# 03 · Differentiating features and MVP scope

**Goal:** decide what makes this app different, what usual basics it still needs, and what is left out of the MVP.
**Done when:** the person approves a short list:
- 4–6 differentiators, each tied to a pain and to why others fail;
- the usual must-haves;
- a "later" list.

## What to ask the person (minimum)
Example questions are in English; translate them into the person's language.
- With the proposal in view: "Is there anything extra, or anything missing that is key for you?"
- Only if the most frequent action is unclear: "What is the first thing someone would do with the app on day one?" In the travel case this changed the scope. Franco: "the important thing is creating the trip, very guided: city, how I arrive, where I stay".
- Nothing else. The agent proposes and the person corrects.

## What the agent does
The coordinator does this alone: no sub-agents, about 10 minutes, working from stage 2.
1. **Differentiators** (4–6). For each one:
   - the pain it solves (from the brief or user voice);
   - how we solve it, in one line;
   - who does it badly today and why (source);
   - the risk taken from the failed apps.

   Travel example: "The day on a map with every leg solved (walk 4 › line 6, 3 stops › walk 2); nothing sends you to another app."
2. **Usual basics:** what the user does most often even if it doesn't differentiate. These usually set the entry flow. Travel: create the trip with flights and lodging → the app builds the trip's skeleton.
3. **Later (nice to have):** everything else, written down so it's not lost. Travel: saving TikToks before the trip, community, reviews and votes.
4. Check the list against the vision principles and the MVP goal. Anything that doesn't serve "used and recommended" moves to Later.

## What gets produced
- `docs/03-scope.html`: one short page, with **no sketches**. Three blocks (Differentiators · Basics · Later), one line each, with the stage 2 links (research summary and gallery) at the top.
- **Canon:** an MVP scope section (in / out). It is used later to check that nothing in scope gets lost.

## Checkpoint
- One message: "This is what came out of the research (3–4 bullets, link). With that, I propose these features (link). Is there anything extra, or anything missing that's key for you?"
- **If they say "I don't know":** say which differentiator you would keep if only one were allowed, and why. Then ask whether that one is right.
- **If they add something that is clearly nice-to-have:** accept it into Later and say so. Don't argue.

## Lessons from the thread
- **Isolated feature sketches can't be judged.** The travel agent drew one sketch per differentiator. Franco: "It was good, but we need to show the features in a complete ideal flow, the full experience of a user using the MVP." Don't draw here; sketches start in stage 4.
- **Watch the nice-to-haves.** Franco: "Careful with NTH, let's focus on what's important and what a user would most usually do. I'm not sure what % would save things beforehand." Rank by frequency × importance, not by novelty.
- **The usual basic flow can be "easy but important" and very guided.** Franco liked "it can be very guided". Don't skip it because it isn't novel.
- **Differentiate against the failed apps, not only the living ones.** The strongest travel differentiators each named the app that died doing the opposite:
  - Google Trips sent you to Maps;
  - Detour built content by hand;
  - Field Trip sent notifications with no plan behind them.
- **Don't name features.** Use plain descriptive working names and mark them as such. The person names things at the end, if at all.
- **Don't let business or tech come back in through the scope.** Neither is part of the MVP decision.
